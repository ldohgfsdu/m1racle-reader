# PDF 菜单原位弹性与长按行高亮

## 用户纠正与视频证据

用户明确指出：卡片不应发生平移，而是原位有 Q 弹感；长按手指所在行需要显示高亮。此前版本误把参考当作拖动卡片，用户未验收通过，不能将之前的自动化通过当作动效符合需求。

重新对 `/storage/emulated/0/Pictures/weixin/VID_20260927_084006.mp4` 的 3–6 秒区域按 8fps 放大逐帧查看：菜单轮廓轻微变化，浅灰圆角背景在“滑动”和“卷页”等行之间切换。视频无触点，具体弹簧参数是近似，不能声称像素/手感完全一致。

## 根因与实现

1. 旧 PdfMenuDrag 把阻尼值用于 Modifier.offset，导致整卡实际平移。删除旧文件、offset 输出和旧位移测试契约；新的 PdfMenuElasticPress 只提供以固定中心为原点的比例形变，手指位移仅用于计算有界 strain，松手弹性恢复。
2. 父层 detectDragGesturesAfterLongPress 消费事件后，子行 clickable 的 PressInteraction 被取消，原来的高亮随之消失。父层现在提供统一的长按手指 root 坐标；各 PdfChromeMenuRow 根据自身实际边界决定高亮，长按期间不再依赖被取消的 rowPressed。
3. 高亮为浅灰圆角背景（onSurface 10%），跨行跟随，移出/松手/取消清除；普通短按仍使用按钮原有按压反馈。长期选中的选项仍由原有勾号表示，不把临时长按状态写成业务选中状态。
4. 主菜单行坐标只在形变完全恢复后登记，二级来源保持原有单一来源；菜单开合形变、二级菜单状态机、PDF 引擎、文档数据和底栏本轮不改。
5. 用户再次指出不跟手，并要求对照原视频。50fps 量到卡片中心约有 10px 的同向位移，灰条落在手指所在行。绕中心缩放会把很高的菜单上沿拉向相反方向，所以上一行不跟手。按住改为有界平移（最大 22dp），松手弹回；行高亮仍按手指所在行立即切换。
