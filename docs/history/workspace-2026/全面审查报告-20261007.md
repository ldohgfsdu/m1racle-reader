### P1-1 对外提供 APK 前的合规裁决：包内含 GPL-3.0-only 派生代码

位置：`app/src/main/java/com/m1racle/reader/ui/hub/RiseDiaryBottomTabs.kt:1-13`、`RiseDiaryGlassButton.kt`、`ui/hub/liquidglass/{DampedDragAnimation, DragGestureInspector, InteractiveHighlight}.kt`（5 个文件均声明 `SPDX-License-Identifier: GPL-3.0-only AND Apache-2.0`，Copyright (C) 2026 sky-shunfengjun）；`LICENSES/RiseDiary-NOTICE.md` 记录为"user-supplied"；生产代码引用自 `ui/hub/DockMotion.kt:8` 等。

影响与事实：

1. 这些文件被编译进 release APK（R8 混淆映射包含对应实现）。
2. GPL-3.0 的对外义务由**分发（convey / distribute）**触发，不由签名、构建或发布渠道触发；向他人提供 APK（包括侧载给他人、任何非公开渠道）即构成分发，不以上架公开市场为条件。纯个人自用不触发对外义务。
3. 缺根 LICENSE、文件头引用的 `LICENSES/Apache-2.0.txt` 不存在（实际为 `LICENSES/RiseDiary-Apache-2.0.txt`）属于仓库说明问题，单独不足以证明违规；是否合规取决于授权链条、分发条款与对应源码提供方式（参见 GNU GPL FAQ: https://www.gnu.org/licenses/gpl-faq.en.html）。
4. 现状：目前可见的仅为个人自用（本人设备安装），未发现对外提供 APK 的记录。因此该项是"对外提供前必须完成的裁决"，不是"已发生的违规"。

建议：在决定对外提供 APK 前，三选一——(a) 用自研或 Apache-2.0 实现替换这 5 个文件对应的交互逻辑并删除 GPL 文件；(b) 接受 GPL-3.0：对外分发时整体以 GPL-3.0 提供，并随包提供对应源码与根 LICENSE，修正引用；(c) 取得权利方（sky-shunfengjun）对闭源分发的明确授权。个人自用阶段无行动要求，但建议尽早裁决以免阻塞发布。

### P1-2 交付版本尚未提交：Git 无法恢复，恢复保障不足

位置：HEAD `a57c324` 的 `app/version.properties` 为 `versionCode=32`；工作树为 `51`。`git log --all -S readium -- app/build.gradle.kts` 为空——即 45–50 版的 Readium 引擎**从未进入任何提交**；提交中的最后一次版本变更停留在 versionCode 32（`2e9a2e3`）。

事实与风险：

1. 71 个已跟踪文件修改 + 55 个未跟踪文件承载了 versionCode 33–51 的全部工作（含已删除的 Readium 路径与当前交付的恢复43版+字体）。交付 APK 由该脏树构建（构建日志 `output/epub-restore43-font/final-build.log`，BUILD SUCCESSFUL 15m13s）。
2. 已验证的源码快照只存在于被 `.gitignore` 排除的 `output/epub-restore43-font/`（`final-production-source.zip` 258 项、`final-test-source.zip`、`before-restore43-source.zip`）与 `.local-backups/`（10-04 的 5 个会话备份）。工作区级备份 `backups/20261003-environment-fixed/` 对应的是 versionCode 31，**不含 33–51**。
3. 因此，`git checkout -- .` / `git clean -fdx` 或磁盘故障后，Git 无法恢复当前交付版本（HEAD 仅到 v32），已交付 APK 亦无法从 Git 重建。存在可救来源——`final-production-source.zip`（258 项，指纹与工作树一致）与 `.local-backups/` 会话备份——但它们未被任何 manifest / sidecar 校验收口，静默损坏或误删无法被及时发现。准确表述是"Git 恢复不可用、整体恢复保障不足"，不是"完全没有恢复来源"。

建议：立即做一次"提交 + 带 manifest 校验的备份"（提交信息可如实说明为会话checkpoint），并将 `final-production-source.zip` 纳入 `backups/` 体系生成 sidecar 与还原说明；之后再继续新工作。这与此前 `reader-r04`、`.local-backups` 的临时做法不同，需要一次性归档动作。

### P2-1 F1 残留：旧空哈希 PDF 被认领后仍指向可变 SAF 源，无读时校验

位置：`DocumentRepository.kt:351-370`（旧记录字节复核后提升哈希，保留原 `uri`）、`:341-342`（PDF 命中复用只更新 `sourceUri/sourceSha256`）；读取侧仅 Markdown 校验哈希（`ViewerViewModel.kt:330`、`DocumentTextReader.kt:7-31`），PDF 打开路径无等价校验；`PdfBodyEditorViewModel.kt:95` 仅在"正文编辑"入口提示 `sourceNeedsUpdate`。

场景：旧版遗留的 null-hash PDF 行在导入同字节文件后被提升为正式身份，但 `uri` 仍指向外部 SAF 文件；用户之后在外部修改该 PDF，阅读器打开的是新字节，而数据库身份、书签、高亮、PDF 目录仍绑定旧内容哈希。相对 Markdown（已冻结私有副本）属于同一类身份缺口，但未被同一条修复覆盖。

建议：身份安全的路径是对 PDF 采用与 Markdown 一致的"导入时冻结私有副本"（首选）。若不冻结，次选可在打开时做有界采样校验，但采样只能发现部分或偶然的变化，**不能保证完整内容身份**，只能作为降级缓解而非等价修复。无论采用哪种，都应把该行为写入 `D1_1_IDENTITY_ARCHITECTURE_DECISION.md`，明确接受的风险范围。
