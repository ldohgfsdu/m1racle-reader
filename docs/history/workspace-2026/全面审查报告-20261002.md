审查日期：2026-10-02（Asia/Shanghai）。对象：本目录中的 Reader 1.0.0 / versionCode 23 备份，Git bundle HEAD `a314247d9cc27f7b3adc1edb3074b65eee3afbfe`。

**结论：备份的主要文件完整，代码有一定的数据安全基础，但发现 3 项 P1、5 项 P2 问题。当前证据不足以通过新版的发布验收。优先处理内容身份、目录写入事务与 EPUB 全书资源预算，再补齐 Windows 自动化和当前 APK 的设备验证。**

### F1 — 内容身份没有始终绑定到可验证的实际字节

位置：[DocumentRepository.kt:316](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/data/repository/DocumentRepository.kt:316)、同文件 353–374、464–472、1024–1027；[ViewerViewModel.kt:330](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/ui/viewer/ViewerViewModel.kt:330)。

主场景：通过 Home SAF 导入 Markdown 内容 A，保存 hash(A)，但 `SOURCE_URI` 保留外部原文档。用户在外部编辑器把它改为 B，阅读页直接读原 URI，没有更新或验证数据库内容哈希。之后从另一 URI 导入内容 A，`findExistingDocument(hash(A))` 命中旧行，提交分支直接返回旧文档，不保留本轮 A 的 staging。结果打开的是 B，系统却认为打开了 A；书签和高亮也继续附着在这个失效的内容身份上。

同一边界的第二个问题：353 行后的 alias 分支在 resolver 未找到相同字节的文档时，仍可仅凭 URI alias 找到 `contentSha256 == null` 的旧行，然后给它赋入本轮 staging 的哈希。尤其是旧 URI 不可读、新 URI 与它共享 canonical alias 时，旧 payload 没有任何字节校验，仍被认领为相同内容。代码声称“only byte-verified aliases”，但这里没有执行该校验。

建议：明确可变源 locator 与不可变内容 identity 的关系。复用前对当前可变 payload 做字节验证，或令 identity 始终指向已验证的不可变副本；读取到内容变化时，明确建立新身份和标注迁移策略。旧 alias 只能用于找候选，不能越过 resolver 的 exact-content 决定。

必要回归：A 导入→外部修改成 B→另一 URI 导入 A，应显示 A；旧 alias 存在但旧 payload 不可读/字节不同，应拒绝盲目认领；验证书签、高亮和笔记不会串到不同内容。

### F2 — PDF 目录写入不能整体回滚

位置：[DocumentRepository.kt:716](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/data/repository/DocumentRepository.kt:716)，合并分支 726；子树删除 671–675。

`importEmbeddedOutline(REPLACE)` 先删除所有节点，再逐条 `upsert`，没有 `db.withTransaction`。MERGE 也逐条提交。任一 DAO 写入失败、页面退出取消 coroutine，或进程在两步之间中断，已删除的旧目录无法回滚，数据库可能仅剩部分新节点。ViewModel 捕获异常后仅提示“导入失败”，不恢复原目录。

建议：在事务外构建导入计划，在一个 Room transaction 内完成替换/合并；对子树删除和批量插入采用相同整体边界。

必要回归：准备旧目录，在第二个新节点写入处注入失败，确认旧目录与所有子节点完整保留；取消时同样验证 rollback。已有文档删除事务测试并不覆盖目录导入这条路径。

### F3 — ZIP 上限不能限制 EPUB 解析后的全书常驻量

位置：[EpubPackageImporter.kt:107](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/epub/EpubPackageImporter.kt:107)，spine 收集 364–370；`EpubXhtmlParser.kt:72`。

EPUB 设置了容器解压 400 MiB、单 XML 8 MiB、单章节 20,000 blocks 等限制，但 `spine.mapIndexed` 把全部章节一次性解析并保存在 `EpubBook.chapters`。章节 block budget 每次解析都会重置，没有累计全书字符数、block 数或 spine 数限制。

更明确的放大入口是重复 `<itemref idref="same"/>`：一个约 1 MiB 的有效章节可以被 5,000 个 spine 引用反复解析并持有，容器依然远低于现有解压与 XML 上限，但模型中的文字总量可达到约 5 GiB，尚未计 DOM 和后续 AnnotatedString 等对象。这里描述的是由代码推出的预算缺口，没有在本机实际分配该内存。

建议：增加全书累计解析预算和 spine 上限；对相同章节资源复用解析结果，并按阅读窗口加载章节。必须在模型增长前拒绝超限输入，不能依赖捕获 `Exception` 处理 `OutOfMemoryError`。

必要回归：大量重复 spine、许多分别低于单章限制的章节、非 linear spine 大量内容；应有确定性 TooLarge 结果，内存使用有界。

### F4 — 残缺 EPUB 解压树可能被永久复用

位置：[DocumentRepository.kt:811](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/data/repository/DocumentRepository.kt:811)；`EpubPackageImporter.kt:110–120`。

缓存有效性仅检查 `META-INF/container.xml` 存在。解压直接写最终目录，中断时可能已存在 container、OPF 和章节文件，但最后一个章节只写了一部分。重开时跳过解压；章节 XML 解析错误被转换为“本章排版异常，已跳过”，整个 book 仍成功返回，因此上层 Corrupt→清缓存重试逻辑不会触发。只要没有手动删除缓存，这个由中断造成的残缺章节会一直被保留。

建议：在临时目录完成解压和校验，成功后原子替换最终目录，并写入绑定内容哈希与 extractor version 的完成标记；没有完成标记的缓存必须重建。区分缓存损坏与源书本来不支持的章节。

必要回归：保留 container/OPF、截断已存在的章节 XML，重开后应重建并恢复原文，不能永久降级为占位。

### F5 — ZIP 导入有两条无界 readText 路径

位置：[DocumentRepository.kt:529](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/data/repository/DocumentRepository.kt:529)；[ZipPackageImporter.kt:139](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/packageimport/ZipPackageImporter.kt:139)。

ZIP 单条目允许 80 MiB；导入时为了取第一个 H1，对入口执行完整 `entry.readText()`，manifest 也整文件读取。阅读阶段却使用 `MAX_MARKDOWN_BYTES = 32 MiB`。所以一个 40 MiB Markdown 入口会在导入阶段整体读入并写入书库，随后阅读必然以 TooLarge 拒绝。80 MiB 的 manifest 或入口还会产生明显的临时文本内存峰值，异常分支仅捕获 Exception。

建议：提取标题只读有界前缀或流式读行；manifest 设置独立的小上限；在提交文档前用同一 Markdown 阅读上限验证入口。

必要回归：超过 32 MiB 的 Markdown 包入口应在导入阶段给出一致的 TooLarge；巨型 manifest 不得整文件读入内存。

### F6 — EPUB 分片只在行之间让出主线程

位置：[EpubTextLayout.kt:232](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/app/src/main/java/com/m1racle/reader/ui/epub/EpubTextLayout.kt:232)、249；`EpubReaderContent.kt:94`。

8ms budget 在每个 row 开始前检查，无法中断随后一次 `measurer.measure`。一个接近 8 MiB XML 上限的单段落、代码块或列表可被合成一个 row，一次 measure 仍可能形成很长的主线程停顿。`epubTextRows()` 也在同步 `remember` 中处理整书，未分片；settings 或 style 变化会再次执行。保留 64 个 layout 的缓存解决了部分常驻量，但不能说明主线程工作已受 8ms 上界约束。

建议：先约束单段长度并把长段落切成保持语义的可测量单元；模型到 rows 的转换使用可取消、有界工作流。对正文规模与输入响应延迟做真机 trace，避免以 row 数代替文字总量。

必要回归/验收：单个超长段落、列表、代码块；长书调整字号期间输入能及时响应，报告实际最大帧耗时。性能影响量级本轮未实测。

### F7 — 原生 Windows 构建被 Unix aapt2 wrapper 阻断

位置：`gradle.properties:11`；[tools/aapt2:1](C:/Users/21234/AppData/Local/Temp/m1racle-audit-20261002/M1racleReader-1.0.0/tools/aapt2:1)。

`android.aapt2FromMavenOverride=../tools/aapt2` 对所有主机生效，目标是以 `#!/bin/sh` 开头的文本脚本，依赖 sed/uname 等，并只寻找 SDK `aapt2`，未处理 Windows 的 `aapt2.exe`。仓库还提供 `gradlew.bat` 和 PowerShell 测试脚本，但安装 JDK/SDK 后的原生 Windows Gradle 路径仍无法直接执行这个 override。

建议：将 ARM/qemu override 限定在需要它的主机本机配置；普通 Windows/x86 主机走 AGP 默认 aapt2，或提供真正的平台专属可执行入口。继续避免把机器绝对路径提交仓库。

证据性质：脚本和全局配置已静态确认；本机当前更早被缺失 Java 阻断，因此没有声称本轮实际走到 aapt2 并复现其进程启动错误。

## 已确认的基础与风险

已确认的优点：实际 APK 没有 INTERNET 权限，`allowBackup=false`；新内容提交使用 ABORT，避免 REPLACE 级联删除阅读资产；文档删除及 PDF 进度/viewport 快照使用事务；私有副本清理有 canonical 路径边界；ZIP/EPUB 解压有路径与字节上限；PDF 覆盖原文件具有 hash 预检、持久备份及回滚；PDF 位图分配有像素上限和 OOM 分支；QA 与生产包使用独立 applicationId，并有防止误跑生产沙箱测试的拒绝入口。

需单独处理的风险，不计作新的已复现缺陷：

1. **签名备份包含明文口令与私钥。** 二者同放在当前分发目录，整个目录一旦被分享即可同时暴露。没有发现泄露事实，本轮也未读取这些文件；建议只以加密容器或密码管理器附件保存签名材料，公开/协作备份应排除 signing 目录。
2. **当前产物缺少当前版本的真机验收。** 源码状态明确记录 09-25 后玻璃、PDF 菜单、EPUB 排版等变化未完成真机验证；旧版本 native crash 闭环不能外推到当前包。
3. **本地验证可持续性不足。** 无 CI；历史 full 基线为 1591 tests / 2 failures，文档归因于 ARM SQLite，不是本轮结果。需在支持的 x86_64 环境重跑，才能确认现在的全量基线。
4. **维护成本集中。** PdfViewerScreen/ViewModel、ContinuousDocumentViewport、DocumentRepository 仍承担较多状态、IO 和生命周期职责；适合独立拆分任务，不建议与上述正确性修复混在一起。源码文本契约测试应辅以行为测试，避免格式断言替代并发与回滚验证。
